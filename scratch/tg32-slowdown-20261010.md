# tg32 Slowdown Diagnostic — 2026-10-10

## A. Executive Summary

**Root cause:** The `reasoning_overflow` retry in `stream_to_vllm` (line 5122) is **NOT gated by** `_no_continue`. When a client-capped request (max_tokens=32) produces all-reasoning output with no content, the retry fires and resets `max_tokens` to the full server budget (22500), completely ignoring the client's 32-token cap.

**Primary offender:** The `reasoning_overflow` non-thinking retry (line 5122-5155). It re-POSTs to vLLM with `enable_thinking: False` and `max_tokens = min(_output_budget(...), MAX_OUTPUT, CTXGATE_MAX_TOTAL_OUTPUT - total_output_tokens)` — which evaluates to 22500, not 32.

**Does `_no_continue` protect against it?** **NO.** The `_no_continue` gate (line 5159) is checked AFTER the reasoning_overflow check (line 5122). The retry fires first, the `continue` statement re-enters the while loop, and the second pass generates hundreds/thousands of tokens before the model stops naturally.

**Impact:** A 32-token request that should take ~0.2s takes 4-20s+ because the retry generates 700-2000+ extra tokens.

**Loop detection (`_detect_loop`):** NOT the primary offender for 32-token requests. The check threshold is 256 chars (LOOP_CHECK_EVERY), and 32 tokens ≈ 100-130 chars, so it never triggers. However, it is also not gated by `_no_continue` and would be a problem for larger capped requests.

### Q8. The reasoning_overflow retry in stream_to_vllm — does the second POST leak past the cap?

**Lines 5128–5131:**
```python
current_body = dict(vllm_body)
current_body["messages"] = list(vllm_body.get("messages", []))
_rb = _output_budget(count_messages_tokens(vllm_body.get("messages", [])))
current_body["max_tokens"] = min(_rb, MAX_OUTPUT, CTXGATE_MAX_TOTAL_OUTPUT - total_output_tokens)
```

Where `_output_budget` (line 2438–2442):
```python
def _output_budget(input_tokens: int) -> int:
    return min(MAX_OUTPUT, MAX_CONTEXT - input_tokens - SAFETY_MARGIN)
```

For 81 input tokens: `_rb = min(22500, 84000 - 81 - 3500) = min(22500, 80419) = 22500`

So: `current_body["max_tokens"] = min(22500, 22500, 50000 - 32) = 22500`

**Answers:**
- **(a)** Does it reuse the same vllm_body with `_ctxgate_no_continue` popped? **YES** — `current_body = dict(vllm_body)` copies the body. `_ctxgate_no_continue` was already popped at line 4800 (`_no_continue = vllm_body.pop("_ctxgate_no_continue", False)`), so it is NOT in the copy.
- **(b)** Use a new body with `_no_continue` still set? **NO** — `_no_continue` is a local variable, not in the body. The body has no `_ctxgate_` keys.
- **(c)** Reset `total_output_tokens`? **NO** — `total_output_tokens` is NOT reset. It retains the 32 tokens from the first pass. But this doesn't matter because `CTXGATE_MAX_TOTAL_OUTPUT - total_output_tokens = 50000 - 32 = 49968`, which is still >> 32.

**The retry leaks past the cap by a factor of 700x** (22500 vs 32). In practice, the model stops generating when it runs out of things to say (709 tokens in our test), but the ALLOWED budget is 22500.

## D. Proposed Fix (do NOT implement)

### Primary fix (addresses the 90x slowdown):

1. **Gate the reasoning_overflow retry with `_no_continue`** (line 5122):
   - Change: `if finish_reason == "length" and not full_content and not tc_accum.count():`
   - To: `if finish_reason == "length" and not full_content and not tc_accum.count() and not _no_continue:`
   - When `_no_continue` is True and this condition would have fired, set `exit_reason = "reasoning_overflow"` and `break` (no retry).

### Secondary fixes (defense in depth for larger capped requests):

2. **Gate `_detect_loop` call sites with `_no_continue`** (lines 5028, 5035, 5387, 5394):
   - Add `and not _no_continue` to the `if not loop_period:` guards.
   - Rationale: For large capped requests (e.g., max_tokens=5000), loop detection could falsely trigger and truncate the response. The client explicitly asked for N tokens; they should get N tokens, not a loop-truncated subset.

3. **Gate the reasoning budget backstop with `_no_continue`** (lines 5044, 5402):
   - Add `and not _no_continue` to the backstop condition.
   - Rationale: Same as above — the client's cap is their explicit choice.

4. **Cap the retry `max_tokens` to the client's cap** (line 5131):
   - Even if we allow the retry for non-capped requests, the retry's `max_tokens` should never exceed the original request's `max_tokens`.
   - Change: `current_body["max_tokens"] = min(_rb, MAX_OUTPUT, CTXGATE_MAX_TOTAL_OUTPUT - total_output_tokens)`
   - To: `current_body["max_tokens"] = min(_rb, MAX_OUTPUT, CTXGATE_MAX_TOTAL_OUTPUT - total_output_tokens, vllm_body.get("max_tokens", MAX_OUTPUT))`
   - Rationale: Prevents the retry from generating more than the client asked for, even in non-capped mode.

### Summary of changes:
| # | Location | Change | Impact |
|---|----------|--------|--------|
| 1 | Line 5122 | Add `and not _no_continue` | **Fixes the 90x slowdown** |
| 2 | Lines 5028, 5035, 5387, 5394 | Add `and not _no_continue` | Prevents false loop truncation on large caps |
| 3 | Lines 5044, 5402 | Add `and not _no_continue` | Prevents false backstop on large caps |
| 4 | Line 5131 | Add client cap to `min()` | Belt-and-suspenders for retry budget |
